# A2A and OpenAPI

LAIX defines the decision and the execution receipt. The host owns the network endpoint, the
authentication and the real action. Two contract files make that boundary portable:

| File | Purpose |
|---|---|
| `packages/contracts/a2a-agent-card.v1.json` | an A2A 1.0 Agent Card template for a decision agent |
| `packages/contracts/action.openapi.v1.json` | an OpenAPI 3.1 profile for a host action endpoint |

Both are templates. Replace the placeholder URL and security scheme before publishing.

## A2A agent card

The card targets A2A **1.0**. In 1.0 the protocol version moved from the top level into
`supportedInterfaces`; do not add a top-level `url` or `protocolVersion`.

```json
{
  "name": "LAIX Decision Agent",
  "supportedInterfaces": [
    {
      "url": "https://your-host.example/a2a",
      "protocolBinding": "JSONRPC",
      "protocolVersion": "1.0"
    }
  ],
  "skills": [{ "id": "decide", "name": "Decide" }]
}
```

The host must:

1. Replace `supportedInterfaces[0].url` with its reachable A2A endpoint.
2. Serve the card at `/.well-known/agent-card.json`.
3. Add `securitySchemes` and `security` if the endpoint is authenticated.
4. Run an A2A server that calls `decide` and returns the decision JSON.
5. Keep the card's `version` in step with the deployed agent, not the A2A protocol version.

LAIX does not ship an A2A HTTP server. The card is the discovery contract; the host implements the
transport and the task lifecycle.

### The `decide` skill

The skill accepts the public `DecisionRequest` JSON and returns the public `Decision` JSON. It does
not execute, deliver or store the decision. Approval, execution and audit remain host concerns.

## OpenAPI action profile

The OpenAPI profile describes the host-owned endpoint that applies an approved decision:

```text
POST /actions/{action_id}
Idempotency-Key: DEC-7F3A2C1B90
```

Request:

```json
{
  "decision_id": "DEC-7F3A2C1B90",
  "trace_id": "TRC-4E2D8A1C77",
  "actor": "incident-bot",
  "approver": "alice",
  "context": { "case_id": "C-1042" }
}
```

Response: an `ExecutionReceipt` with `id`, `decision_id`, `action_name`, `status`, `actor`, `detail`,
`error`, `approved_by` and `idempotency_key`.

The path `action_id` must match the decision's `action_id`. The idempotency key is required. A
timeout or lost response should return an `unknown` receipt and be reconciled before a retry.

The profile exposes these extensions:

| Extension | Meaning |
|---|---|
| `x-laix-decision-schema` | the public decision schema URL |
| `x-laix-decision-verbs` | the seven verbs |
| `x-laix-receipt-statuses` | the receipt statuses, matching the code |

## Which integration to use

| Client | Use |
|---|---|
| A model or desktop tool that speaks MCP | [MCP server](05-mcp.md) |
| Another agent or orchestrator | the A2A Agent Card |
| A host action service | the OpenAPI action profile |
| A Python or TypeScript app | the package API directly |

They are complementary. MCP exposes `decide` as a tool; A2A advertises the decision agent to other
agents; OpenAPI describes the host action boundary. None of them makes LAIX own execution.

## Security

- The A2A endpoint and the action endpoint need the host's authentication and authorization.
- Do not publish an unauthenticated action endpoint.
- Keep secrets and raw customer content out of the card and the OpenAPI document.
- Treat the A2A card and OpenAPI document as public contracts; review changes like API changes.

## Validation

The repository tests check:

- A2A 1.0 field placement, the `decide` skill and the JSON media types;
- optional parsing with the A2A SDK when installed;
- OpenAPI 3.1 structure, the idempotency header, the receipt statuses and the decision schema link;
- optional validation with `openapi-spec-validator` when installed.
